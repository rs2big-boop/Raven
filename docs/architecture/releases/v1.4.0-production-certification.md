## 1. Clean Release Build Verification

### Purpose & Scope
Ensures that all binaries, static libraries, and test harnesses compile reproducibly from a completely clean, unpolluted workspace under strict release compiler optimization flags (`-O3 -DNDEBUG -std=c++20`), without depending on temporary or cached build artifacts.

### Measurable Acceptance Criteria
1. Compilation succeeds from an empty build directory with **zero errors** and **zero compiler warnings** under `-Wall -Wextra -Wpedantic`.
2. Binary outputs are generated and verified at their expected output paths:
   - CLI Driver: `build/bin/raven` (or `build/raven`)
   - Bytecode Compiler: `build/bin/ravenc` (or `build/ravenc`)
   - Corvus Virtual Machine: `build/bin/rvm` (or `build/rvm`)
   - Time-Travel Debugger: `build/bin/rvndb` (or `build/rvndb`)
   - Core Static Library: `build/libraven_core.a`
3. Stripped production binaries execute `--version` cleanly without missing shared library symbols.

### Exact Build & Verification Commands
```bash
# 1. Clean previous build artifacts
rm -rf build_release
mkdir -p build_release

# 2. Configure with strict release flags
cmake -B build_release \
  -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_CXX_FLAGS="-O3 -DNDEBUG -Wall -Wextra -Wpedantic" \
  -DRAVEN_ENABLE_ASAN=OFF \
  -DRAVEN_ENABLE_UBSAN=OFF \
  -DRAVEN_ENABLE_TSAN=OFF

# 3. Compile clean release target
cmake --build build_release --clean-first -j$(nproc)

# 4. Binary sanity smoke test
./build_release/raven --version
./build_release/ravenc --version
./build_release/rvm --version
```

### Mandatory Release Blockers (Never Release If)
- Any compiler warning or error is generated during clean build.
- Missing symbol resolution during static link phase.
- Executables segfault or abort during `--version` invocation.

## 3. Extended GC Stress Testing & Soak Qualification

### Purpose & Scope
Proves long-term runtime stability and validates that continuous allocations, generational promotions, and concurrent Stop-The-World (STW) safepoint pauses do not lead to gradual heap exhaustion, memory leaks, or thread deadlocks over prolonged execution intervals.

### Measurable Acceptance Criteria
1. **10-Minute Continuous GC Stress**: Sustained allocation and collection with zero invariant violations.
2. **Resident Memory Bound**: RSS growth ≤ 20% from first to last sample (`EXPECT_LT(growth_pct, 20.0)`).
3. **Concurrent Mutators**: Minimum of 4 worker threads performing intense Arc allocation/deallocation while GC runs continuous STW and Sweeps.
4. **Zero Lockups**: No deadlock, livelock, or unnotified condition variable hangs.

### Test Implementation
`BenchmarkSuite.ExtendedSoakTest` — built into `memory_benchmarks`. Runs in CI at 500 ms (fast feedback). For the full Gate 3 qualification, run with `RAVEN_SOAK_MS=600000` (10 minutes). Samples `/proc/self/status VmRSS` every 2 s and asserts RSS growth ≤ 20%.

### Exact Execution Commands
```bash
# CI quick smoke (500 ms — always runs in ctest)
./build_release/memory_benchmarks --gtest_filter="BenchmarkSuite.ExtendedSoakTest"

# Full 10-minute Gate 3 qualification soak with live RSS sampling
RAVEN_SOAK_MS=600000 ./build_release/memory_benchmarks \
  --gtest_filter="BenchmarkSuite.ExtendedSoakTest"
```

### Verified Empirical Soak Test Qualification
```

Mutator Threads   : 4 concurrent mutators
Total Mutator Ops : 101,812,247 operations (1,696,870 ops/sec)
```

### Mandatory Release Blockers (Never Release If)
- Process terminates with `SIGSEGV`, `SIGBUS`, `SIGABRT`, or assertion failure.
- RSS growth exceeds 20% from start to end of soak run.
- Deadlock between mutator thread parking and safepoint coordinator.

## 4. Stack Map Completeness Audit

### Purpose & Scope
Guarantees that every bytecode instruction capable of triggering garbage collection or reaching a safepoint emits an exact, validated `StackMap` in `chunk.stack_maps`. Coverage scope (commit `adddaf8`):

| Opcode | Reason | Covered |
|:---|:---|:---:|
| `OpCode::Loop` | Back-edge — GC poll point | ✅ |
| `OpCode::Call` | Function / pipeline invocation | ✅ |
| `OpCode::BuildArray` | Heap allocation — may trigger GC | ✅ |
| `OpCode::BuildMap` | Heap allocation — may trigger GC | ✅ |

### Measurable Acceptance Criteria
1. Automated audit pass disassembles the complete instruction stream of compiled chunks.
2. For every covered opcode offset, `chunk.stack_maps.find_map(offset)` returns a valid, non-null pointer.
3. The associated StackMap contains precise operand stack and local variable reference bitmaps.
4. Test source exercises all four opcode classes (loop, call, array literal, map literal).

### Exact Audit Test Commands
```bash
# Run automated completeness audit
./build_release/memory_tests --gtest_filter="MemoryTest.StackMapCompletenessAudit"
```

### Mandatory Release Blockers (Never Release If)
- Any covered opcode offset lacks a registered `StackMap`.
- Stack map bitmap length does not match compiler local variable scope depth.
- Roots on operand stack or locals are skipped by root scanner during STW pause.

## 9. Final Architecture Review & Memory Engine Freeze

### Architecture Status
- **Ownership & Move Semantics**: Compile-time move enforcement, use-after-move detection, reassignment revival (`ADR 0008.1`).
- **Resource Operation Leases**: Concurrent `ResourceControlBlock`, active leases barrier, non-blocking asynchronous Reaper (`ADR 0008.2`).
- **Concurrent Arc Registry**: 32 striped partitions aligned on 64-byte cache boundaries (`alignas(64)`), Fibonacci bitmask hashing (`& 31`), zero cross-thread false sharing.
- **Corvus Safepoint Engine**: Polling at loop back-edges, call sites, array and map allocations, precise `StackMapTable`, deadlock-free Native Thread Parking.
- **Generational GC**: Card Table dirty indexing, Old $\to$ Young write barrier, incremental grey shading.

### Memory Engine Freeze Agreement
Upon successful completion of the Stage 4 checklist, the Memory & Resource Engine is officially **FROZEN**. No fundamental structural rewrites or exploratory concurrency changes are permitted in subsequent minor releases without an approved Architectural Decision Record (ADR) and rigorous empirical performance justification.
